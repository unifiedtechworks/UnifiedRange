# Account Deletion Implementation Plan

Updated: 2026-09-05. Status: implementation proposal only; deletion remains disabled.

## Scope and repository baseline

This document refines [Account Deletion Plan](ACCOUNT_DELETION_PLAN.md) and [Account Data Lifecycle Plan](ACCOUNT_DATA_LIFECYCLE_PLAN.md). It proposes future work only: no runtime, schema, IAM, or public image changes are included. Pair it with [Data Export Implementation Plan](DATA_EXPORT_IMPLEMENTATION_PLAN.md).

The implementation inventory is `amplify/data/resource.ts`, `amplify/storage/resource.ts`, `amplify/auth/resource.ts`, `amplify/backend.ts`, `src/lib/usernameReservationData.ts`, and the image handlers. Cognito uses email sign-in with `admin`/`moderator` groups; the application username is separate. Only `UserProfile.ownerId` and `PublicImageAsset.publicPassportSnapshotId` have explicit secondary indexes. There is no account lifecycle/job model, global write gate, retention store, or background account cleanup worker.

Phase 2C processing, 2D consent, 2E delivery, and 2F removal already have specific invariants. [Phase 2F lifecycle cleanup](PUBLIC_IMAGE_PHASE_2F_LIFECYCLE_CLEANUP_PLAN.md) removes derivatives without deleting private originals; account deletion must eventually coordinate both. The existing owner mutation is not a complete account cleanup service and requires authenticated caller context. Do not fabricate that context for a background job.

## Proposed policy and user experience

- Recommend a 24-hour cancellation window, starting only after backend acceptance. These durations are product proposals, not deployed behavior or statements of legal requirements.
- During `pendingDeletion`, block ordinary writes, publishing, uploads, and new exports. Permit only authenticated lifecycle status/cancellation. Withdraw public content promptly after acceptance; preserve a private recovery inventory until commitment. Cancellation restores account access but requires explicit republishing and fresh image consent; it must not silently restore public visibility.
- At the deadline, atomically move to `deletionInProgress`. Cancellation loses that conditional race and is no longer available. Hard-delete ordinary content after this point. Soft deletion is only a temporary workflow state, never the final privacy outcome.
- Explain private record/image loss, removal of public content and authored comments, report exceptions, username reservation, cancellation deadline, backups, and the irreversible boundary. Offer export before requesting deletion and advise downloading it first; never silently create or email an export.
- Notify the verified channel on request, cancellation, and completion without content or tokens. A completion notice distinguishes ordinary-data removal from retained exceptions and backup expiry. Prepare any required notification before removing Cognito/contact data; discard transient delivery information after bounded delivery attempts.

## Identity, re-authentication, and enforcement

Require an interactive Cognito sign-in, including configured challenges, within a proposed five-minute freshness window, plus explicit deletion confirmation. The backend validates issuer, signature, audience/client, token use, expiry, stable subject, and authentication time. Token refresh alone and a recent `iat` are not re-authentication. Bind a short-lived, one-use confirmation challenge to the subject, action, and policy version; consume it atomically with request creation. Do not accept passwords into the job API or log authentication payloads. Future federated sign-in needs equivalent provider-backed freshness tests.

Resolve the stable user-pool subject and proven legacy owner aliases on the server; existing image code recognizes subject and Cognito username forms. Never use the editable app username, request-supplied owner IDs, or string guesses as authority. Resolve and durably capture all proven identity-pool storage identities before identity removal. `PrivateImageAsset.storageIdentityId` and browser-created candidate rows alone are not proof. Missing or ambiguous historical mappings require restricted reconciliation, not guessed prefix deletion or a success result.

A dedicated lifecycle store must enforce account state across direct AppSync model mutations, custom Lambdas, username claim/repair, public publishing, and S3 uploads. Include writes by other users targeting a deleting account's content. Existing generated owner rules and UI guards do not implement this. Future resolver/backend and storage authorization work is a launch prerequisite; do not add it in this docs task. Gate both operation admission and final commit with an account generation to stop in-flight recreation.

Revoke sessions at commitment and deny normal application access while keeping the worker independent of live user credentials. Retain Cognito identity until data verification finishes, then delete it. This refines the older plan's ordering: keep identity for cleanup but do not rely on it remaining usable. JWT signature/expiry checks can still accept revoked tokens, so sign-out alone is not the write gate. See [Cognito token revocation](https://docs.aws.amazon.com/cognito/latest/developerguide/token-revocation.html). Existing identity-pool credentials and presigned uploads also need an enforced deny or a tested expiry/drain barrier followed by a final sweep; deletion cannot finish while late writes remain possible.

## Treatment by data class

| Data / ownership selector | Required treatment |
| --- | --- |
| `UserProfile.ownerId` | Capture only required identity mapping, then delete after dependencies. Clear profile caches. |
| `EquipmentPassport`, `ProjectileProfile`, `OpticSightProfile` by `ownerId` | Hard-delete all owned records, including unpublished records, notes, counters, and image references. Do not rely on cascading deletes. |
| `RangeSession`, `TargetPhoto`, `MaintenanceLogEntry`, `HuntingChecklist` by `ownerId` | Delete children before parents. Validate references without treating a foreign parent ID as ownership. Inventory orphan rows independently. |
| `PrivateImageAsset` by proven `ownerId`/`ownerSub` | Cover every binding state, including unverified, failed, rejected, and removed. Preserve cleanup evidence until S3 verification, then delete ledger rows. |
| Private S3 images | Enumerate proven `private/equipment/{identityId}/` and `private/targets/{identityId}/` prefixes, including unregistered uploads and abandoned files. Reconcile `privateCoverPhotoKey`, `TargetPhoto.storageKey`, and asset bindings. Never follow arbitrary URLs. |
| `PublicPassportSnapshot.ownerId` | Withdraw and hard-delete all snapshots, including embedded `publicRangeSessions`, `publicStats`, and photo placeholders. There is no separate public range-session snapshot model today. |
| `PublicUserProfileSnapshot.ownerId` | Remove the whole public identity snapshot; visibility flags alone do not prevent API-key reads under the current schema. No publicly linked account tombstone. |
| `PublicImageAsset.ownerId` and snapshot relationship; derivative S3 objects | Retire all states and historical/orphan assets, not just the currently attached cover. Delete derivatives after revoking delivery; keep private cleanup evidence until verified. |
| `Comment.authorId` | Recommend hard deletion of all authored comments, including hidden/reported comments on other accounts' targets. Retaining body text with a generic author is not sufficient anonymization. This resolves the older plan's optional anonymization in favor of deletion. |
| `Reaction.userId` | Delete authored reactions across all targets; reconcile affected aggregate counts if any are introduced. |
| Other users' comments/reactions on deleted targets | Delete target-dependent social rows as content closure, not as requester-owned data. Match `(targetType, targetId)` for private passport/session and public snapshot IDs. Preserve only approved restricted report evidence. Do not delete unrelated contributions. |
| `Report.reporterId` and reports targeting deleted content/comments | Preserve only approved moderation facts in restricted retention storage, redact identifying narrative, sever public identity links, then remove ordinary copies as appropriate. Do not bulk-delete reports submitted by others merely because their target is removed. |
| `UsernameReservation.ownerId` | Inventory all owned reservations, including stale rename/repair leftovers. Conditionally replace with non-identifying tombstones; never release a reservation now owned by another account. |
| Export artifacts/staging and lifecycle manifests | Cancel/fence export workers and purge artifacts, multipart uploads, and staging. Remove detailed cleanup manifests after verification; keep only bounded audit receipts. |

## Username and moderation retention

Recommend a 90-day username quarantine after commitment, with automatic conditional release unless a documented, expiring abuse hold applies. Retain only normalized username, expiry, and policy/reason code in a backend-only tombstone store; remove the original subject/owner linkage. Never attach old public URLs, comments, or profile data to a new claimant. Availability returns only unavailable, without exposing deleted-account history. Expiry is checked during atomic claim processing; delayed TTL removal cannot decide availability. Claim, rename, and repair must all respect tombstones. Current reservations are authenticated-readable and have required `ownerId`, so storing a raw deletion marker there is not a complete design; a future backend-controlled claim path and authorization design are prerequisites.

Recommend retaining minimized closed report cases for 180 days after closure; review open cases every 30 days and require an explicit renewal decision at 180 days. Retain necessary reason/category, target-unavailable marker, workflow status, timestamps, and decision evidence. Restrict moderator audit attribution separately when accountability requires it; do not erase another moderator's accountability or expose it through exports. The current `Report` stores only current status/timestamps, not a review history or enforcement ledger. Designing that protected history is future work, not an existing capability.

Reports currently allow reporter deletion and moderators can update only status. Reliable retained evidence therefore needs a backend-owned retention path and future authorization changes before launch. Redact free-text `details` and identity-bearing reasons; a pseudonymous reference remains sensitive if linkable. Do not automatically retain private images or whole private records as evidence. Each exception needs a purpose, authorized reviewer, minimal scope, expiry, access log, and periodic review. A hold applies only to specified evidence, not to continued public availability or the whole account. Record retained exceptions separately from cleanup failures. Retention numbers, backup schedules, notice wording, and hold authority require product/privacy review before implementation is enabled.

## Backend job design and ordered execution

Propose authenticated request/status/cancel Lambdas plus a durable Step Functions Standard workflow with bounded page workers, scheduled reconciliation, and a backend-only DynamoDB job/checkpoint store. API names and stores are new design concepts, not existing schema fields. Clients send confirmation proof and an idempotency key, never object keys or owner selectors. Jobs contain an opaque ID, protected subject mapping, policy version, account generation, deadline, step cursor, lease, attempt count, counters, error code, retention exceptions, and timestamps. Store large inventories privately outside workflow payloads; restrict state-machine execution history and logs.

1. **Accept and freeze:** conditionally create one active deletion job per subject, consume confirmation, fence competing exports, and enforce write/public access gates. Persist ownership and cleanup evidence before withdrawing snapshots. Failure to withdraw remains an alerted in-progress task.
2. **Pending window:** serve status/cancel through the restricted authenticated path. On cancellation, record outcome and discard unnecessary inventory; on expiry, atomically commit, revoke sessions, and drain/fence active writers.
3. **Inventory:** paginate every owned model, social author selector, target-dependent relation, reservation, private prefix, derivative prefix, and artifact. Use existing indexes only as discovery aids. Propose future owner/author/reporter/target indexes with backfill verification. Until then use bounded, capacity-limited backend scans with explicit ownership filtering; never a single client list page. Persist opaque references and protected exact keys before deleting source rows.
4. **Withdraw public data:** revoke new image delivery, retire assets, and remove public profile/passport snapshots from direct APIs and application caches. Keep the inventory available independently after snapshot removal. Respect current canonical derivative grammar `public/passports/{snapshotId}/cover/{publicImageAssetId}.jpg`. Discover historical/orphan derivatives only under independently proven owned snapshot prefixes; ambiguous keys block their cleanup rather than broadening scope.
5. **Retain/minimize social evidence:** create idempotent restricted case records before removing identifying social rows. Handle reports about the user's content and reports submitted by the user independently. Reconcile target references and any counters.
6. **Purge objects:** remove private originals, derivatives, export artifacts, temporary files, and abandoned multipart uploads. Paginate object/version inventories. Check bucket versioning, replicas, and retention locks in the deployed environment; remove permitted historical versions and delete markers explicitly. A delete marker alone is not erasure: [S3 DeleteObject](https://docs.aws.amazon.com/en_en/AmazonS3/latest/API/API_DeleteObject.html). Do not bypass a valid hold; report its bounded exception.
7. **Purge ordinary records:** delete dependent private/social rows, image ledgers after object verification, parents, and finally profile. Finalize reservation tombstones transactionally against expected ownership. Use conditioned writes and tolerate already-absent items.
8. **Verify and remove identity:** repeat inventories after writers and credentials are fenced/drained. Require zero remaining ordinary owned/target-dependent rows, objects/versions, or artifacts, and no new public delivery. Then delete Cognito using the captured server identity; already-absent user is idempotent success. Independently reconcile any applicable identity-pool mapping only after storage cleanup. Failure here stays resumable.
9. **Finalize:** record `completed` or `completedWithRetainedExceptions`, notify, and expire sensitive manifests/mappings. Backups follow documented expiry and restore suppression; do not claim instantaneous erasure of backups or copies previously downloaded by others.

Public image delivery currently issues a maximum 60-second URL. Removing snapshots stops new resolution but cannot recall downloaded images. Verify object removal and the residual URL/cache window separately. Account cleanup must eventually use a reviewed backend service that retains Phase 2F conditional-detach, ownership, and removed-ledger invariants and handles snapshot absence; do not change those handlers in this task. Late processors must be fenced before final sweep and must not recreate artifacts or projections.

## Retry, completion, audit, and operations

Use at-least-once-safe steps: conditional transitions, leases with expiry, monotonically increasing fencing generations, deterministic evidence IDs, and per-page checkpoints. Do not mark a page complete before all actions are acknowledged. Retry throttling/timeouts with bounded exponential backoff and jitter; retry DynamoDB unprocessed items and individual S3 batch errors. A timeout after deletion must be resolved by re-read. Ownership conflicts fail closed. Exhausted retries enter `needsAttention`; they never reactivate the account or report success. Operators resume the same job with audited access rather than start an untracked cleanup.

IAM separates lifecycle coordination, destructive workers, retention writers, and audit readers. Limit tables, actions, and prefixes; jobs revalidate ownership even with server IAM. No API-key lifecycle endpoints and no inherited moderator right to export/delete private accounts. Audit only opaque job references, actor class, policy version, transition, count, timestamp, and bounded outcome; keep raw identities/keys only in short-lived encrypted operational manifests. Never log tokens, signed URLs, filenames, image bytes, profile text, report narratives, or private record contents. Proposed minimal receipt retention is 180 days with a separate restore-suppression record lasting through the longest backup retention period; approve and enforce both before launch.

On backup restore, isolate the environment, replay deletion/retention suppression, and verify before enabling traffic. Track backup expiry dates, holds, access, and eventual purge. Alert on overdue jobs, public-withdrawal failures, ambiguous storage identity, retention expiry failure, and Cognito finalization failure. Provide a restricted runbook for retries, evidence review, and independently verified completion.

## Delivery sequence and acceptance gates

1. Approve policy defaults and retention/hold/backup inventory; capture current schema and deployed storage/auth behavior.
2. Build shared ownership inventory and export first; validate full pagination and cross-account denial.
3. Add future lifecycle stores, backfilled indexes, backend authorization/write gates, storage fencing, and username/retention services in separately reviewed implementation changes.
4. Build deletion dry-run and resumable workers; integrate public-image lifecycle only in its own reviewed change preserving all phase boundaries.
5. Add re-authentication, impact confirmation, cancellation, bounded status, and notifications; keep the feature disabled until sandbox tests pass.
6. Test empty/large/multi-page accounts; legacy aliases and multiple storage identities; orphan images/rows; all asset states; shared target IDs across types; third-party reports; stale reservations and reclaim races; every step's crash/retry; cancel-vs-commit; old JWT/STS credentials; late uploads/processors; Cognito failure; S3 versions/holds; backup restoration; no cross-account reads/deletes; logs free of sensitive content. Verify direct API-key snapshot access is gone, not only UI hiding.

Release requires a dry-run/reconciliation report, least-privilege review, successful failure-injection tests, retention purge tests, and an operations owner. For this documentation-only change run `npm run amplify:typecheck`, `npm run lint`, `npm run build`, and `git diff --check`; these checks do not establish deployed deletion correctness.
